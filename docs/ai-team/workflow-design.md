# ออกแบบระบบ Workflow — แตกงานใหญ่ → กระจายทีม → เจ้าของคุมแผน

เอกสารออกแบบ (ยังไม่ลงมือเขียนโค้ด) สำหรับให้โมเดลถัดไปนำไป implement
เขียนจากโจทย์ของคุณปาล์ม: *"โยนงานว่าอยากทำนามบัตร → เลขาต้องคิดมาว่ามีขั้นตอนอะไรบ้าง ใช้ข้อมูลตรงไหน → กระจายให้แต่ละ AI → มี Workflow ให้กดดูได้ → แจ้งเตือนว่ากำลังทำอะไร → ฉันเข้ามาคอมเมนต์ปรับแผน"*

---

## 1. ทำไมตอนนี้ยังไม่เป็นแบบนั้น (วินิจฉัยก่อนออกแบบ)

**กลไกแตกแผนงานมีอยู่แล้วในระบบ** — `[[PLAN]]` → `createProjectPlan()` → `pushPlanForApproval()` → `approveProject()` → `advanceProject()` ปลดล็อกทีละขั้น และใน `SYSTEM_PROMPT` ใช้ตัวอย่าง *"ทำนามบัตรให้ทีมขาย"* ตรงกับเคสนี้เป๊ะ

แต่งาน #REQ260812-8592 *"อยากทำนามบัตรทีมเซลล์"* กลับลงเป็น **งานเดี่ยว** ไม่ใช่โปรเจกต์ สาเหตุ:

| # | สาเหตุ | หลักฐาน |
|---|---|---|
| 1 | **คำสั่งถูกกลืน** — `SYSTEM_PROMPT` ตอนนี้ยาว ~90 บรรทัด กฎ PLAN อยู่กลางดง แข่งกับกฎการเงิน/อนุมัติ/แผนก/มารยาทกลุ่ม | prompt ยาวขึ้น 3 เท่าจากตอนแรก |
| 2 | **โมเดลเล็กเกินสำหรับงานคิดแผน** — Haiku 4.5 ต้องทำ 6 อย่างพร้อมกันใน 1 รอบ (สวมบุคลิก + กรองการเงิน + คัดแยกงาน + เลือกแผนก + ตัดสินว่าเดี่ยวหรือโปรเจกต์ + ออกแบบแผน) | งานคิดแผนคือส่วนที่ยากสุด แต่ได้ความสนใจน้อยสุด |
| 3 | **ข้อความสั้น** — "อยากทำนามบัตรทีมเซลล์" 4 คำ ไม่มีสัญญาณว่าใหญ่ | โมเดลเลือกทางที่ง่ายกว่า = TASK |
| 4 | **ไม่มีตัวบังคับ** — ถ้าโมเดลเลือกผิด ไม่มีอะไรตรวจ | ไม่มี validation ระหว่าง TASK/PLAN |

> **บทเรียนหลักของการออกแบบรอบนี้:** อย่าหวังให้ prompt เดียวทำทุกอย่าง
> **แยก "การคิดแผน" ออกมาเป็นขั้นตอนของตัวเอง ที่มี prompt เฉพาะและโมเดลที่เหมาะ**

## 2. ภาพรวมระบบใหม่

```
คุณปาล์ม/ทีม พิมพ์ในไลน์ ─┐
ฟอร์มบนบอร์ด ────────────┴─→ [ขั้น 1: คัดแยก]  ← Haiku ใน GAS (ถูกมาก)
                                    │
                        งานเดี่ยว ──┴── งานหลายขั้น
                             │              │
                             │       [ขั้น 2: วางแผน]  ← Sonnet ใน GAS (เรียกเฉพาะตอนจำเป็น)
                             │              │  ← "Planner Skill" อยู่ตรงนี้
                             │              ↓
                             │       ร่างแผน + ระบุว่าใช้ข้อมูลจากไหน
                             │              ↓
                             │       📱 แจ้งไลน์ + ลิงก์เปิดหน้า Workflow
                             │              ↓
                             │       👤 คุณปาล์มดู/คอมเมนต์/ตัดขั้น/อนุมัติ
                             │              ↓
                             └──────→ [ขั้น 3: ลงมือ]  ← Claude Code Routine (แพงสุด)
                                            ↓
                                     กระจาย subagent ตามแผนก
                                            ↓
                                     📱 รายงานความคืบหน้า → วนกลับให้คอมเมนต์
```

**หลักการที่ทำให้ประหยัด:** งานคิด (ถูก) ทำใน GAS / งานลงมือ (แพง) ทำใน Routine
และ**ให้เจ้าของอนุมัติคั่นกลาง** — ทุกขั้นที่ถูกตัดทิ้งตอนอนุมัติ คือ token ที่ไม่ถูกใช้เลย

## 3. ใครถือ "Skill" การวางแผน — เลขาหรือใคร

**คำตอบ: เลขา** แต่ต้องเป็น "หมวกคนละใบ" ไม่ใช่ prompt เดียวกับตอนคุยเล่น

| | เลขาโหมดคุย (มีอยู่แล้ว) | เลขาโหมดวางแผน (ของใหม่) |
|---|---|---|
| ไฟล์/ฟังก์ชัน | `SYSTEM_PROMPT` + `askClaude()` | `PLANNER_PROMPT` + `askPlanner()` |
| โมเดล | `claude-haiku-4-5` | `claude-sonnet-5` |
| เรียกเมื่อ | ทุกข้อความ | เฉพาะตอนเจองานหลายขั้น (~5-10% ของข้อความ) |
| หน้าที่ | ตอบ/รับเรื่อง/คัดแยก | ออกแบบแผนอย่างเดียว ไม่ต้องมีบุคลิก |
| ผลลัพธ์ | ข้อความตอบ + บล็อก TASK | JSON แผนงานล้วน |

**เหตุผลที่ไม่ยกไปให้ Routine ทำ:** Routine 1 รอบ ≈ **760,000 token** (ตัวเลขจริงจากรอบที่รันไปแล้ว)
ส่วนเรียก Sonnet ใน GAS 1 ครั้ง ≈ **6,000 token** — ถูกกว่า **120 เท่า** และได้แผนใน 5 วินาที ไม่ต้องรอรอบ

## 4. โครงสร้างแผนงาน (Plan Schema)

ของเดิมมีแค่ `{dept, detail, needs}` ซึ่งตอบคำถาม *"ใช้ข้อมูลตรงไหนบ้าง"* ไม่ได้ ของใหม่:

```jsonc
{
  "title": "นามบัตรทีมเซลล์",
  "biz": "โรงน้ำ",
  "goal": "นามบัตรพร้อมส่งโรงพิมพ์ ครบทุกคนในทีมขาย",
  "why": "ทีมขายออกพบลูกค้าแล้วไม่มีนามบัตรให้",       // เลขาสรุปเหตุผลเอง
  "risks": ["ถ้าชื่อ-ตำแหน่งผิด ต้องพิมพ์ใหม่ทั้งชุด"],   // ให้เจ้าของเห็นจุดเสี่ยงก่อนอนุมัติ
  "steps": [
    {
      "no": 1,
      "dept": "data",
      "detail": "รวบรวมรายชื่อทีมขาย: ชื่อจริง-นามสกุล ตำแหน่ง เบอร์ อีเมล",
      "inputs": [
        { "kind": "sheet", "ref": "พนักงาน", "note": "ถ้ามีแท็บนี้อยู่แล้ว" },
        { "kind": "ask", "ref": "sales", "note": "ถามในกลุ่มทีมเซลล์ถ้าข้อมูลไม่ครบ" }
      ],
      "output": "ตารางรายชื่อพร้อมใช้",
      "dependsOn": [],
      "needsHuman": false,
      "estMinutes": 10
    },
    {
      "no": 2,
      "dept": "content",
      "detail": "ออกแบบนามบัตร 3 คอนเซป ใช้สี/โลโก้จากคลังแบรนด์",
      "inputs": [
        { "kind": "drive", "ref": "BRAND_KIT", "note": "โลโก้ + สีแบรนด์" },
        { "kind": "step",  "ref": 1,           "note": "ต้องรู้ว่ามีกี่คน/ตำแหน่งอะไร" }
      ],
      "output": "ไฟล์ดีไซน์ 3 แบบ + เหตุผลแต่ละคอนเซป",
      "dependsOn": [1],
      "needsHuman": false,
      "estMinutes": 20
    },
    {
      "no": 3, "dept": "เจ้าของ",
      "detail": "เลือกคอนเซปที่ชอบ",
      "dependsOn": [2], "needsHuman": true, "estMinutes": 5
    },
    {
      "no": 4, "dept": "procurement",
      "detail": "เทียบราคาโรงพิมพ์ 3 เจ้า (ในจังหวัด + ออนไลน์)",
      "dependsOn": [], "needsHuman": false, "estMinutes": 15   // ← ไม่ผูกกับขั้น 1-3 ทำขนานได้
    }
  ],
  "openQuestions": ["ทีมขายมีกี่คน?", "อยากได้กี่ใบต่อคน?"]
}
```

**ของใหม่ที่สำคัญ 3 อย่าง:**

1. **`inputs[].kind`** — ตอบโจทย์ *"ใช้ข้อมูลตรงไหนบ้าง"* ตรง ๆ
   `sheet` (แท็บไหน) / `drive` (โฟลเดอร์ไหน) / `ask` (ต้องถามใคร) / `step` (รอผลขั้นก่อน)
   → ระบบเห็นล่วงหน้าว่าข้อมูลขาด แล้ว **ยิง `askInfo` ตั้งแต่ตอนวางแผน** ไม่ใช่ไปตันตอนทำ

2. **`dependsOn`** — เดิมล็อกเรียง 1→2→3→4 เสมอ ทั้งที่ขั้น 4 (เทียบราคาโรงพิมพ์) ไม่ต้องรอใคร
   → ขั้นที่ไม่ผูกกัน **ปลดล็อกพร้อมกัน ทำใน Routine รอบเดียว** = เร็วขึ้นและ**ประหยัด token มาก** (ดูข้อ 7)

3. **`needsHuman`** — แยกชัดว่าขั้นไหน AI ทำไม่ได้ ต้องเตือนคน (มี `notifyHumanStep()` รองรับแล้ว)

   │    ⏱️ เริ่ม 09:15   [💬] [✕ ตัดขั้นนี้]

**ปุ่มที่ต้องมี** (ต่อยอดจากที่ทำไปแล้ว):
- `💬` ต่อขั้น — คอมเมนต์เฉพาะขั้นนั้น (`rpcComment` รองรับ ref รายขั้นอยู่แล้ว)
- `✕ ตัดขั้นนี้` — ลบขั้นออกจากแผน **ก่อนเสียtoken** ← ปุ่มประหยัดเงินที่สุดในระบบ
- `➕ แทรกขั้นตอน` — เพิ่มขั้นเอง (เขียนลงชีตตรง ๆ ไม่กิน token)
- `⚡ เริ่มเลย` รายขั้น — ปลดล็อกขั้นที่ทำขนานได้โดยไม่ต้องรอ

**ทางเข้า:** `?page=board&key=...&prj=PRJ260812-4471` — ใช้ลิงก์นี้ในข้อความไลน์ได้เลย

## 6. การแจ้งเตือน — บอกให้พอดี ไม่รำคาญ

| จังหวะ | ส่งอะไร | ทำไม |
|---|---|---|
| **ร่างแผนเสร็จ** | สรุปแผน + `openQuestions` + ปุ่มเปิด Workflow + วิธีอนุมัติ | จุดตัดสินใจสำคัญที่สุด |
| **จบรอบทำงาน** (ไม่ใช่ทุกขั้น) | สรุปรวบเดียว: *"รอบ 10:00 ทำ 3 งาน / เสร็จ 2 / ติด 1"* | กันสแปม — เดิมยิงทุกงานที่เสร็จ |
| **ถึงขั้นที่ต้องให้คนทำ** | เตือนพร้อมวิธีปิดงาน | ไม่งั้นโปรเจกต์ค้าง |

| **โปรเจกต์จบ** | สรุปผลรวม + ลิงก์ | มีอยู่แล้ว |

> **แก้ของเดิม:** ตอนนี้ `handleCompleteTask` ยิงไลน์ทุกงานที่เสร็จ ถ้าโปรเจกต์มี 6 ขั้น = เด้ง 6 ครั้ง
> ควรเปลี่ยนเป็น**สรุปรอบละครั้ง** และเก็บรายละเอียดไว้ในหน้า Workflow

## 7. ⚠️ Token — ส่วนที่คุณปาล์มเป็นห่วง

### 7.1 ตัวเลขจริงจากระบบคุณ (ไม่ใช่การประมาณ)

| ส่วน | token ต่อครั้ง | ที่มา |
|---|---|---|
| คุยกับเลขาในไลน์ 1 ข้อความ | **~4,000** (cache ช่วยเหลือ ~90%) | Haiku + prompt caching |
| **Routine รัน 1 รอบ** | **~870,000** | วัดจริง: cache read 758K + cache write 104K + output 9.4K |
| แชทห้องนี้ (คุยกับผมทั้งวัน) | **~22,500,000** | วัดจริงจาก session metadata |

**เทียบให้เห็นภาพ:**
```
คุยเลขาในไลน์ 1 ข้อความ  ▏                      (1 หน่วย)
Routine 1 รอบ            ████████████████████   (218 หน่วย)
แชทห้องนี้ทั้งวัน         ████████████████████████████████... (5,600 หน่วย)
```

> 💡 **ข้อสรุปที่สำคัญที่สุด: ตัวกิน token อันดับ 1 คือแชทห้องนี้ ไม่ใช่ระบบอัตโนมัติ**
> แชทวันนี้ห้องเดียว = Routine รัน **26 รอบ** = คุยกับเลขาในไลน์ **5,600 ข้อความ**
> ระบบอัตโนมัติที่สร้างมาทั้งหมด **ไม่ใช่ต้นเหตุที่ token หมดไว**

### 7.2 ระบบใหม่จะกินเพิ่มเท่าไหร่

| ขั้นตอน | token | หมายเหตุ |
|---|---|---|
| คัดแยกว่าเป็นงานใหญ่ไหม | +0 | รวมอยู่ในข้อความที่คุยอยู่แล้ว |
| **วางแผน (Sonnet ใน GAS)** | **~6,000** | เรียกครั้งเดียวต่อโปรเจกต์ |
| แจ้งเตือน / คอมเมนต์ / อนุมัติ / หน้า Workflow | **0** | เขียนอ่านชีตล้วน ไม่แตะ Claude |
| **ลงมือทำ (Routine)** | **~870,000 ต่อรอบ** | ← ตัวจริงที่ต้องคุม |

**ดังนั้นตัวแปรเดียวที่มีผลจริงคือ: โปรเจกต์นี้ใช้ Routine กี่รอบ**

| วิธีทำ | จำนวนรอบ | token รวม |
|---|---|---|
| ❌ ล็อกเรียง 1→2→3→4 (ของเดิม) | 4 รอบ | **~3,500,000** |
| ✅ ใช้ `dependsOn` ปลดล็อกขั้นที่ขนานได้ | 2 รอบ | **~1,740,000** |
| ✅✅ + ตัด 1 ขั้นที่ไม่จำเป็นตอนอนุมัติ | 2 รอบ | **~1,740,000** และงานเสร็จเร็วขึ้น |

### 7.3 🔴 จุดรั่วที่ใหญ่ที่สุด (แนะนำแก้ก่อนอย่างอื่น)

**Routine ตั้งไว้ทุกชั่วโมง 8:00–18:00 = 11 รอบ/วัน — รอบที่คิวว่างก็ยังเสีย token**
เพราะทุกรอบต้องบูต session, clone repo, อ่าน `CLAUDE.md` ก่อนจะรู้ว่าไม่มีงาน

```
สภาพตอนนี้:  11 รอบ/วัน × ~870K ≈ 9,500,000 token/วัน   ← ส่วนใหญ่คิวว่าง
```

**ทางแก้: เปลี่ยนจาก "ตั้งเวลาถาม" เป็น "มีงานค่อยเรียก"**
โครงสร้างพร้อมแล้ว — `fireRoutine()` ยิง `/fire` ได้ และปุ่ม ⚡ ก็ใช้ทางนี้อยู่

```
เสนอ:  งานเข้าคิว/ได้รับอนุมัติ → GAS ยิง /fire ทันที   (มีงานเมื่อไหร่ ทำเมื่อนั้น)
       + ตั้งเวลาสำรองวันละ 2 รอบ (เช้า 8:15 / เย็น 17:15) กันงานตกหล่น

ผลลัพธ์:  ~3 รอบ/วัน ≈ 2,600,000 token/วัน   ← ลดลง ~73%
          และงานเริ่มทำทันที ไม่ต้องรอถึงชั่วโมงถัดไป (เร็วขึ้นด้วย)
```

**ต้องกันยิงซ้ำ:** debounce 5 นาที (มี `STALE_MIN` เป็นต้นแบบอยู่แล้ว) — ฝากงานรัว 3 งานใน 1 นาที ต้องยิงรอบเดียว

### 7.4 มาตรการคุม token อื่น ๆ (เรียงตามความคุ้ม)

| # | มาตรการ | ลดได้ | แรงที่ใช้ |

## 9. สรุปให้ผู้บริหารตัดสินใจ

1. **ระบบแตกแผนมีอยู่แล้ว แต่พัง** เพราะยัดทุกกฎไว้ใน prompt เดียวให้โมเดลเล็กทำ →
   แก้ด้วยการ**แยกขั้นวางแผนออกมา ใช้ Sonnet เฉพาะตอนจำเป็น** (+6,000 token/โปรเจกต์ ถือว่าฟรี)
2. **หน้า Workflow, คอมเมนต์, อนุมัติ, ตัดขั้น — ไม่กิน token เลยสักหน่วย** เพราะเป็นการอ่านเขียนชีตล้วน
   ยิ่งคุณใช้หน้านี้คุมแผนมากเท่าไหร่ ยิ่งประหยัด เพราะตัดงานที่ไม่จำเป็นทิ้งก่อน AI ลงมือ
3. **จุดรั่วจริงคือ Routine รายชั่วโมงที่รันตอนคิวว่าง** — แก้แล้วประหยัด ~73% และงานเดินเร็วขึ้นด้วย
4. **แต่ตัวกิน token อันดับ 1 คือแชทกับ Claude Code ห้องนี้ (22.5M)** ไม่ใช่ระบบอัตโนมัติ (9.5M/วัน)
   ถ้าจะประหยัดจริงจัง: คุยห้องนี้เท่าที่จำเป็น สั่งงานผ่านบอร์ด/ไลน์แทน — ถูกกว่า 5,600 เท่าต่อครั้ง
